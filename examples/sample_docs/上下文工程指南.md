# 上下文工程指南

## 一句话定义

上下文工程解决的是「这一轮到底把哪些信息交给模型」的问题。

它不等同于提示词工程：提示词工程优化的是**指令怎么写**，
上下文工程优化的是**在有限 token 预算内，保留哪些信息、丢弃哪些信息、
以什么顺序和形式组织它们**。

## Token 预算为什么必须分区

把所有信息塞进一个总预算里，会出现一个典型故障：
检索片段很长时，历史对话被挤掉；历史很长时，检索片段被挤掉，
而系统提示词这种**绝对不能丢**的内容也可能被裁掉。

因此 ContextForge 把预算拆成六段，各段只在自身额度内裁剪：

| 分区 | 内容 | 是否能丢 |
| --- | --- | --- |
| system | 系统提示、行为准则 | 否 |
| memory | 长期记忆、可用技能 | 可降级 |
| retrieved | 检索片段（含引用编号） | 可丢，按分数从低到高 |
| history | 历史对话（摘要 + 近期原文） | 可压缩 |
| tools | 工具定义 | 可取舍 |
| current | 当前用户问题 | 否 |

关键原则：**任何一段超支都不允许挤占其他段的额度**。
额度用尽时的行为是「在这段内部做取舍」，而不是「全局抢占」。

## 四种压缩策略及其代价

- **none（不压缩）**：作为实验基线。token 成本最高，但信息零损失。
- **sliding（滑动窗口）**：只保留最近若干轮。最省 token，
  但会不可逆地丢失早期目标和约束 —— 例如用户在第 1 轮说的
  「必须用中文回答」会消失。
- **summary（抽取式摘要）**：把旧轮次压成一段带标记的背景信息。
  成本中等，用「关键词优先级 + 时间衰减」挑选要保留的句子。
- **hybrid（混合策略，默认）**：先用正则线索**钉住**关键约束
  （目标、必须、不要、约定、结论……），再对剩余内容做抽取式摘要，
  最后保留最近若干轮原文。这是唯一能在压缩的同时保证
  「硬约束保留率 = 1.0」的策略。

## 压缩必须以轮次为单位

这是整个上下文工程里最容易踩的坑。

一次工具调用在消息列表里长这样：

```
assistant(tool_calls=[{id: "call_1", ...}])
tool(tool_call_id="call_1", content="...")
```

这两条消息是**强绑定**的。如果压缩或裁剪时把 assistant 的调用留下、
把 tool 的结果丢掉（或者反过来），发给模型的上下文就是非法的，
请求会直接失败。

所以所有压缩策略都共享一条硬约束：**以「轮次」为最小单位**，
一个轮次从 user 消息开始，到「不带 tool_calls 的 assistant」结束，
中间的 tool_calls 与 tool 结果永不拆开。

任何压缩动作之后，都要重新跑一遍工具调用链完整性校验，
确认每一个 `tool_call_id` 都有唯一的、成对的匹配。

## 旧方法与新方法的差别

| 做法 | 问题 |
| --- | --- |
| 按字符数估算 token | 中英文混排误差可达数倍 |
| 超预算就直接砍消息 | 会把摘要和约束先砍掉（方向反了） |
| 靠「把近期轮数从 3 试到 0」硬试 | 没有记录为什么丢、丢了什么 |
| 只输出压缩后的消息 | 无法回答「压缩效果到底如何」 |

ContextForge 的答案：可插拔 token 计数器、以轮次为单位的压缩、
超预算时先降低保留轮数再降级、以及一份**上下文构建报告**——
报告里写清每个分区用了多少 token、丢了哪些片段、压缩率是多少。
没有这份报告，「上下文效率」就只是一个说法，而不是一个可验证的数字。
