# 检索与重排序

## 为什么单一检索不够

**向量检索**把文本映射到向量空间，擅长「意思相近但用词不同」的情况，
但它对精确词经常失灵：函数名 `compress_history`、报错码 `E501`、
版本号 `v2.3.1`、专有名词，这些词在向量空间里可能和一堆无关内容挤在一起。

**BM25** 是经典稀疏检索：基于词频与逆文档频率打分，
对精确词命中的效果非常好，但完全无法处理同义改写 ——
用户问「怎么精简上下文」，它匹配不到写着「压缩上下文」的文档。

两类检索召回的文档集合往往只有部分重叠。
把它们融合，能在不显著增加成本的前提下同时提高召回与精度。

## 融合：为什么优先选 RRF

**RRF（Reciprocal Rank Fusion）** 只用「排名」，不用「分数」：

```
score(d) = Σ_i  1 / (k + rank_i(d))     k 通常取 60
```

它的价值在于：向量余弦相似度的取值范围是 [-1, 1]，
BM25 的分数没有上界（实测可能到 10 以上）。直接加权相加时，
必须反复调参才能让两路势均力敌，而且换个语料就要重调。

**加权融合**（先把两路分数各自归一化到 0~1 再加权）也可以，
但它对异常值敏感：某一路的最高分如果是个离群点，
归一化之后其余分数会被整体压低。

RRF 对分数量纲不敏感，因此**鲁棒性更好**，
这也是它成为混合检索默认选择的原因。

## 重排序解决什么

融合阶段只看排名，并不真正衡量「查询和这段文本到底有多匹配」。
所以还需要一次**重排序**：用更贵的特征，对少数候选重新打分。

ContextForge 使用轻量的启发式重排序器，特征包括：

1. **查询词覆盖率**：查询的 token 有多少出现在片段里（权重 0.50）
2. **短语命中**：查询的归一化字符序列在片段中的最长公共子串占比（0.25）
3. **标题命中**：标题 token 与查询词的重叠（0.10）
4. **长度先验**：太短信息不足、太长噪声多且占预算（0.15）

最终分数 = 0.7 × 重排序分 + 0.3 × 融合分，
即「精细匹配为主，召回先验为辅」。

生产环境可以把这个启发式重排序器替换成交叉编码器
（bge-reranker、Cohere Rerank 等），只要实现
`score(query, chunk) -> float` 这一个接口。

## 完整链路

```
查询
  ├─ 稠密检索（向量，余弦）        → top 12
  └─ 稀疏检索（BM25-Okapi）        → top 12
              ↓
        RRF 融合（k=60）           → top 16
              ↓
        启发式重排序               → top 5（带引用编号）
              ↓
        交给上下文引擎按预算装配
```

每一步的命中数、耗时都会写入检索轨迹，用于定位「效果差在哪一环」。
