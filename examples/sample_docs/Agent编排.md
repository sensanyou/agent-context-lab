# Agent 编排

## 为什么需要「图」而不是「链」

线性调用链只能表达「A 然后 B 然后 C」。真实任务不是这样的：

- 模型可能一轮调用多个工具，也可能一轮都不调；
- 工具失败需要重试；
- 证据不足需要**回头再检索一次**；
- 长任务中途可能需要人工确认。

这些是**条件分支、循环与中断恢复**，用 `if/else` 写在一段过程式代码里
会迅速失控。把它们显式建模成图，才能让控制流可读、可测、可恢复。

## ContextForge 的工作流

```
prepare ──┬─> retrieve ──> build_context ──> reason ──┬─> tools ──> build_context（循环）
          └──────────────────────────────────────────  ├─> reflect ─┬─> build_context（重试）
                                                        │            └─> finalize
                                                        └─> finalize
```

### 每个节点只做一件事

| 节点 | 职责 |
| --- | --- |
| prepare | 取长期记忆与技能先验；让模型做任务规划 |
| retrieve | 混合检索，返回带分数的片段 |
| build_context | **调用上下文引擎组装本轮消息**（含预算与工具链校验） |
| reason | 模型基于当前上下文决定调用工具还是作答 |
| tools | 执行工具、记录结果、写回会话 |
| reflect | 检查回答是否有证据支撑，不足则请求重试 |
| finalize | 会话落库、沉淀长期记忆、结束任务 |

### 三个控制流各自解决什么

- **循环 `tools → build_context → reason`**
  模型可能连续调用多个工具。注意每次循环都要**重新组装上下文**：
  工具输出可能很长，上一轮刚好装得下，这一轮就超预算了。
  这正是「上下文管理必须是运行时公共能力」的原因 ——
  它不是某个节点的私有逻辑，而是每轮都要过的一道闸门。

- **条件分支 `reason → tools / reflect / finalize`**
  走向由**模型自己的输出**决定（有没有 tool_calls），
  而不是由代码写死。想让 Agent 换一种策略，改的是提示词，不是控制流代码。

- **重试 `reflect → build_context`**
  证据不足时自动再检索一次，而不是把「我不知道」直接抛给用户。
  重试次数受 `max_iterations` 约束，避免死循环。

## 状态设计与可恢复性

状态对象 `AgentState` 里**只放可序列化的数据**。
模型客户端、数据库连接、向量矩阵全部放在运行时上下文（`RuntimeContext`）里。

原因很直接：任务一旦要跨请求恢复，状态就必须能被完整地写进检查点再读回来。
把不可序列化的对象混进状态，恢复时就只能重建半个现场。

检查点在每个节点执行前后各写一次，因此：

- 任意一步崩溃，都能从最近的检查点继续；
- `interrupt_before=["tools"]` 可以让人工确认后再执行工具；
- `resume(thread_id)` 从检查点续跑，不会重复已经完成的步骤。

## 状态合并语义

节点不读取已有内容，只返回**增量**：

- 列表字段（`observations`、`tool_executions`、`events`）是**追加**语义；
- 其他字段是**覆盖**语义。

这样节点之间没有隐式依赖，单测时传入一个只含必要字段的状态即可运行，
重放或并行执行时也不会因为读取顺序而丢数据。
